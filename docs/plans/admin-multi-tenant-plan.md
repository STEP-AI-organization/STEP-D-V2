> - **한글 회사 이름이 전부 같은 id(`t__`)** 로 유도돼 두 번째 한글 회사부터 409 였다.
>
> 용어: 사용자에게 보이는 글에서는 "테넌트"라 쓰지 않는다 (CLAUDE.md "용어" 참조).

> 목적: `admin.stepd.stepai.kr` 콘솔이 **회사 여러 곳을 실제로 운영**할 수 있게 한다.

## 0. 결정 사항 (2026-08-11 · 사용자)

| 질문 | 결정 |
|------|------|
| 과금 모델 | **크레딧 선불 단일.** 월정액+초과분(`plans`·`subscriptions`·`invoices`)은 만들지 않는다 |
| 회사별 API 키 | **지금 만든다.** 고객사 시스템이 우리 API를 호출하는 방향 |
| 운영자 열람 범위 | **운영자는 전부 볼 수 있어야 한다** |

세 번째 결정은 "다른 워크스페이스 것이 보이면 안 된다"는 제품 원칙과 부딪히는 것처럼 보이지만,
층이 다르다. **워크스페이스 사용자끼리는 서로 안 보이고, 플랫폼 운영자는 다 본다.**
격리를 지키는 주체가 RLS 라면, 운영자 경로는 그 RLS 를 합법적으로 우회하는 유일한 문이고
이미 그렇게 설계돼 있다(`index.ts` "격리를 합법적으로 우회하는 유일한 경로다").
이번 작업은 그 문을 넓히는 것이지 새 구멍을 뚫는 게 아니다.

읽기·쓰기를 다르게 대한다:
- **읽기** — 사유 없이 허용. 운영자가 매번 사유를 적어야 하면 지원이 안 굴러간다. 감사 기록은 남긴다.
- **쓰기** — 사유 강제 + 감사(기존 `requireReason` 유지).

## 1. 지금 상태 (실측)

### 어드민 콘솔 — 5화면 686줄

`Overview` · `Tenants` · `Users` · `Jobs` · `Audit`.
할 수 있는 것: 회사 생성/이름·상태 변경, 사용자 목록/정지/초대, 잡 목록, 감사 로그, 전체 요약.
서버 라우트 9개(`/api/superadmin/*`), 전부 `requireSuperadmin` + 감사 기록.

### DB 는 이미 다회사용으로 짜여 있다

마이그레이션 0023·0024 로 `plans` · `subscriptions` · `usage_events` · `invoices` ·
`api_keys` · `credit_ledger` · `credit_topup` 이 프로덕션에 들어가 있다. RLS 도 걸려 있다.
스키마 자체는 잘 설계돼 있다 — `api_keys` 는 `key_hash`/`prefix` 를 나눠 두고 "평문은 발급
순간에만 1회 노출" 을 주석으로 못박아 뒀다.

### 그런데 표를 쓰는 코드가 없다

|----|----------------|
| `api_keys` | **0** |
| `invoices` | **0** |

### 크레딧은 반대로 잘 돌고 있다

(2026-08-11 ₩1,680 실결제). 즉 **과금의 실제 동선은 크레딧 하나뿐이고, 그게 잘 돈다.**

## 2. 확인된 구멍

### 구멍 1 — 회사 정지가 아무것도 막지 않는다 ⚠️ 최우선

`PATCH /api/superadmin/tenants/:id` 로 `status='suspended'` 를 써도 **행 하나가 바뀔 뿐이다.**

- 사용자 정지는 `destroyAllSessions()` 를 부른다 (`index.ts:581`, `769`).
  **회사 정지는 안 부른다** (`index.ts:722~`).
- 로그인은 `user.status !== "active"` 만 본다. `tenants.status` 는 안 본다.
- 세션 검증 쿼리(`auth.ts:203`)도 `users` 만 읽고 `tenants` 를 조인하지 않는다.
- 잡 큐도 회사 상태를 보지 않는다.

→ **미납·계약종료된 회사를 못 막는다.** 정지 버튼이 있는데 안 먹는 게 없느니만 못하다.

### 구멍 2 — 회사를 만들면 반쪽으로 남는다

회사 생성(`POST /api/superadmin/tenants`)과 첫 관리자 초대
(`POST /api/superadmin/tenants/:id/invite`)가 **따로**다. 두 번째가 실패하면 아무도 못 들어가는
회사가 남는다. 초기 크레딧 지급도 별도 경로가 없다.

### 구멍 3 — 회사 단위로 볼 수가 없다

`Users` · `Jobs` · `Audit` 이 전부 전역 목록이다. "이 회사가 지금 어떤 상태인지"
— 사용자 몇 명, 이번 달 몇 분 썼고, 크레딧 얼마 남았고, 잡이 밀렸는지 — 를 한 화면에서 못 본다.
회사가 2~3곳일 땐 견디지만 10곳이 되면 못 쓴다.

### 구멍 4 — API 키 경로가 통째로 없다

표만 있고 발급·검증·회수가 없다.

## 3. 작업 계획

### 0단계 — 정지 실효화 (구멍 1) ✅

가장 작고 가장 급하다. 새 표 없이 배선만으로 닫힌다.

- 세션 검증 쿼리에 `tenants` 조인 → 회사가 `active` 가 아니면 세션 무효
- 로그인에도 같은 검사. 거부 사유를 **구분해서** 준다 —
  "비밀번호 틀림"과 "회사가 정지됨"은 사용자가 할 일이 다르다
- `PATCH /api/superadmin/tenants/:id` 에서 `suspended`/`closed` 로 바뀌면
  그 회사 전 사용자 세션 파기
- 잡: 큐잉 시점 차단 + 워커 claim 시점 재확인(둘 다 — 큐잉 후 정지되는 경우가 있다)

**테스트로 잠근다** (F3 게이트와 같은 급): 정지된 회사의 세션이 죽는지, 로그인이 거부되는지,
잡이 안 도는지. 서버 테스트다, UI 테스트가 아니다.

### 1단계 — 죽은 과금 코드 정리 (결정 반영) ✅

크레딧 단일로 정했으므로 `plans` 기반 경로는 **의도적으로 안 쓰는 것**임을 코드에 명시한다.

- `billing.ts` 의 `checkQuota` · `buildInvoice` · `planLine` · `usageLine` 과
  그 테스트를 제거. 남기면 "있는 줄 알고" 다음 사람이 배선하려 든다
- `plans` · `subscriptions` · `invoices` **표는 지우지 않는다** — 계약형이 필요해질 때
  스키마를 다시 설계하는 비용이 더 크다. 대신 마이그레이션 주석에 "미사용 · 2026-08-11 결정" 을 단다
- `credits.ts` 의 `balanceOf`/`checkCredits` 가 `db-pg` 의 SQL 판정과 **중복**이다.
  둘 중 하나로 정리(순수 함수를 남기고 db-pg 가 그걸 쓰는 방향)

### 2단계 — 회사 온보딩 원자화 (구멍 2) ✅

- `POST /api/superadmin/tenants` 하나로: 회사 + 첫 owner 초대 + 초기 크레딧을 **한 트랜잭션**
- 반환값에 초대 링크 완성형(지금은 토큰만 준다)
- 어드민 "회사 추가" 폼: 회사명 · 구분 · 청구 이메일 · 첫 관리자 이메일 · 초기 크레딧

### 3단계 — 회사별 API 키 (구멍 4) ✅

**핵심 원칙: 키 인증도 세션과 똑같이 `app.tenant_id` 를 세팅하는 경로를 지난다.**
RLS 가 이미 격리를 담당하므로, 키 경로가 그걸 우회하면 격리가 두 벌이 되고 한 벌은 반드시 샌다.

서버:
- `POST /api/superadmin/tenants/:id/api-keys` — 평문 **1회만** 반환, 저장은 sha256
- `GET  /api/superadmin/tenants/:id/api-keys` — prefix · scopes · last_used_at · revoked_at
- `POST /api/superadmin/api-keys/:keyId/revoke` — 사유 강제
- 인증 미들웨어: `Authorization: Bearer stepd_live_…` → sha256 조회 → 폐기/정지 확인 →
  `app.tenant_id` 설정 → `last_used_at` 갱신(매 요청 쓰기는 과하다 · 1분 스로틀)
- **정지된 회사의 키는 거부** (0단계와 같은 검사를 탄다)
- scope 최소 집합부터: `media:write` · `search:read` · `clips:read`
- **고객사에 열 라우트를 화이트리스트로 명시.** 세션용 라우트 118개를 통째로 열면 안 된다

테스트: 폐기된 키 거부 · 정지 회사 키 거부 · A사 키로 B사 데이터 접근 불가 · 평문 미저장.

### 4단계 — 어드민을 회사 중심으로 재구성 (구멍 3) — 대부분 완료

- **회사 목록**: 이름 · 구분 · 상태 · 사용자 수 · 이번 달 분석 분 · 잔여 크레딧 · 마지막 활동
- **회사 상세 한 화면**(탭): 개요 / 사용자 / API 키 / 크레딧 원장 / 잡 / 감사
- 전역 `Users`·`Jobs`·`Audit` 은 남기되 **회사 필터**를 붙인다
- 감사 로그 검색(지금은 전체 목록만) — 운영자가 다 볼 수 있게 된 만큼 견제가 더 중요해진다

### 5단계 — 큐 공정성 (회사 수가 늘면 필수, 지금은 아님) — 미착수

`job_queue` 는 FIFO + 레인이다. 한 회사가 100건을 넣으면 나머지 회사가 전부 뒤에 선다.
회사별 라운드로빈 claim 이 필요하다. **회사 3곳까진 안 아프다** — 그래서 후순위.

## 4. 하지 않는 것

- `plans`/`subscriptions`/`invoices` 배선 — 크레딧 단일 결정
- 대행(운영자가 고객사 대신 조작) — 이번엔 **열람까지**. 필요해지면 별도로 결정
- 프론트(`apps/web`) 변경 — 전면개편 중이라 손대지 않는다

## 5. 순서와 근거

```
0단계 정지 실효화   ← 지금 안 되는 게 제품 신뢰를 깎는다. 제일 작고 제일 급하다
1단계 죽은 코드 정리 ← 0단계 하면서 같이. 안 하면 다음 사람이 헷갈린다
2단계 온보딩 원자화 ← 회사가 늘기 시작하면 매번 아프다
3단계 API 키       ← 영업 자산. 계약 협의 때 보여줄 게 생긴다
4단계 어드민 재구성 ← 위 셋이 다 붙어야 보여줄 내용이 생긴다
5단계 큐 공정성     ← 회사 5곳 넘어가면 그때
```

비용: 전 단계가 **코드 작업이라 ₩0** (재분석 없음). 각 단계 끝에 배포가 필요하고,
배포는 명시 요청 시에만 한다.
