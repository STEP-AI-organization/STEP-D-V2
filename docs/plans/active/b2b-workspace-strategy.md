## 0. 한 장 요약

STEP D는 **회사 단위 워크스페이스를 파는 B2B SaaS**다. 회사 하나 = 워크스페이스 하나이고,
그 안에서 프로그램·영상·클립·배포채널·성과가 전부 격리된다. 남의 워크스페이스는 보이지 않는다.

고객사가 STEP D를 쓰는 길은 **두 개**이고, 둘 다 같은 워크스페이스로 들어온다.

```
① 사람이 화면에서       stepd.stepai.kr 로그인 → 업로드·검수·채택·배포
② 고객사 시스템이 API로  Authorization: Bearer stepd_live_… → 영상 넣고 결과 가져감

                        ↓ 둘 다

              같은 워크스페이스 · 같은 데이터 · 같은 크레딧 원장
```

**KT ENA 건이 ②의 첫 실제 사례다.** ENA 워크스페이스를 하나 만들고, ENA의 자체 백엔드(AENA)에
그 워크스페이스 소속 API 키를 발급한다. AENA가 영상을 던지면 STEP D가 분석·쇼츠·클립·YouTube 배포까지
완주하고, 그 결과물은 전부 ENA 워크스페이스에 쌓인다 — ENA 담당자가 웹에 로그인하면 **API로 만들어진
그 데이터를 화면에서 그대로 이어서** 만질 수 있다.

이게 이 설계의 핵심 판매 논리다. **API는 별도 상품이 아니라 워크스페이스의 두 번째 입구다.**

## 1. 왜 이 모양인가

### 안 그랬으면 어땠나

예전 구조에는 **소유자 개념이 아예 없었다.** 데이터에 "누구 것"이 안 적혀 있으니
외부 방송사를 하나만 받아도 A사가 B사 회차를 본다. 그 상태로는 영업 자체가 불가능하다.

동시에, 초기 factory API는 **글로벌 단일 키(`x-factory-key`)** 였다. 키 하나를 모두가 공유하니
누가 얼마나 썼는지 알 수 없고 = 과금이 불가능하고, 데이터를 어디에 귀속시킬지도 정할 수 없었다.

두 문제의 답이 같다: **워크스페이스(테넌트)를 데이터·과금·인증의 공통 단위로 만든다.**

### 그래서 정한 것 세 가지

| 결정 | 내용 | 근거 |
|---|---|---|
| **격리 주체** | 애플리케이션 WHERE 절이 아니라 **DB의 RLS** | 조회 함수 ~100개에 손으로 WHERE를 붙이면 한 군데만 빠뜨려도 유출인데, 빠뜨린 걸 타입도 테스트도 못 잡는다 |
| **API 인증** | 글로벌 키 폐기 → **워크스페이스 API 키** | 키가 곧 테넌트 정체성이어야 과금·귀속·격리가 한 번에 선다 |
| **과금** | 월정액/구독 아님 → **선불 크레딧 단일** | 실제로 도는 동선이 크레딧 하나뿐이고 잘 돈다. 요금제 표는 만들어놓고 아무도 안 썼다 |

## 2. 용어 — 같은 실체를 자리마다 다르게 부른다

`tenants` 테이블의 행 하나를 가리키는 말이 세 개다. **섞어 쓰면 고객이 못 알아듣는다.**

| 자리 | 쓰는 말 | 왜 |
|---|---|---|
| 어드민 콘솔 (`admin.stepd.stepai.kr`) | **회사** | STEPAI 운영자가 여러 고객사를 관리하는 자리 |
| 제품 화면 (`stepd.stepai.kr`) · 오류 메시지 | **워크스페이스** | 사용자는 자기 것 *안에* 있다 |
| 코드 · DB · 기술 문서 | `tenantId` · `tenants` | 그대로 둔다. 리네임은 위험만 크고 얻는 게 없다 |

**사용자에게 보이는 글에 "테넌트"라고 쓰지 않는다.**

워크스페이스 하나 = 회사 하나. 그 안에 직원이 여러 명 있고 서로의 작업을 같이 본다.
처음에 owner 계정 하나를 주고, 그 사람이 동료를 초대하면 초대받은 사람이 또 초대할 수 있다.

`tenants.kind` 는 세 값을 갖는다 — `internal`(사내) · `web`(웹 고객) · `api`(API 고객).
모르는 값은 **가장 좁은 쪽(`api`)으로 떨어뜨린다**. `internal`이 실수로 붙으면 안 되기 때문이다.

`tenants.status` 는 `active` · `suspended` · `closed`.

## 3. 격리는 어떻게 지켜지는가 — 3중, 전부 fail-closed

"실수하면 유출"이 아니라 **"실수하면 안 보임"** 이 되도록 방향을 잡았다. 세 겹이다.

### 겹 1 — DB가 직접 막는다 (RLS)

`migrations/0014_tenant_rls.cjs`. 23개 표 전체에 정책을 건다.

```
커넥션마다  set_config('app.tenant_id', <테넌트>)  를 먼저 심는다
정책이 그 값과 행의 tenant_id 를 비교한다

  값이 특정 테넌트  →  그 테넌트 행만 보인다
  값이 '*'          →  전 테넌트 (스케줄러·워커 등 시스템 작업만)
  값이 없음(NULL)   →  아무 행도 안 보인다   ← 배선을 빼먹으면 유출이 아니라 빈 결과
```

> ⚠️ **`FORCE ROW LEVEL SECURITY`가 필수다.** `ENABLE`만 걸면 **테이블 소유자는 정책을 우회한다.**
> 우리 앱은 보통 소유자 역할로 접속하므로 ENABLE만으로는 아무것도 안 막힌다.

`tenant_id`는 파생 테이블까지 **전부 denormalize**했다(부모를 조인하지 않는다).
조인으로 스코프를 잡으면 조인 하나 빼먹은 쿼리가 곧 유출이다.

### 겹 2 — 코드가 스코프를 들고 다닌다 (`tenant.ts`)

`AsyncLocalStorage`로 요청·잡 단위 컨텍스트를 흘린다. 스코프가 없으면 **던진다.**

```ts
// tenant.ts
export function currentScope(): TenantScope {
  const ctx = als.getStore();
  if (!ctx) throw new Error("tenant scope missing — …");
  return ctx.scope;
}
```

여기서 "기본 테넌트로 폴백"을 만들지 **않은 것**이 핵심이다. 폴백이 있으면 배선을 빼먹어도
화면이 멀쩡히 뜨고, 그 상태로 외부 방송사를 받는 순간 유출된다.

전 테넌트 횡단이 필요하면 `runAsSystem()`으로 **의도를 적어야** 한다.

> 실제로 이걸로 잡힌 사고: `getRawPool()`로 RLS 표를 만지던 5곳이 에러가 아니라 **0행**을 내고 있었다.
> 어드민 개요·잡·회사 규모가 전부 0이었다. `asSystem()`으로 통일하고 `rls-access.test.ts`로 잠갔다.

### 겹 3 — 자세가 어긋나면 서버가 안 뜬다 (`assertAuthPosture`)

테넌트가 2개 이상인데 `AUTH_REQUIRED`가 꺼져 있으면 **모든 요청이 `t_default`로 해석된다** = 격리가 무의미하다.
그 조합을 기동 시 잡아 `/health` 외 전 라우트를 **503**으로 막는다.

```
테넌트가 N개인데 AUTH_REQUIRED 가 꺼져 있다 — 모든 요청이 t_default 로
해석되어 테넌트 격리가 무의미해진다. AUTH_REQUIRED=1 로 켜거나, 추가 테넌트를 정리할 것.
```

**사람이 기억하는 데 기대지 않는다.** ENA 워크스페이스를 만드는 순간 이 조건이 발동하므로,
`AUTH_REQUIRED=1`이 **워크스페이스 생성보다 먼저**다.

## 4. 두 개의 문 — 사람(세션)과 시스템(API 키)

요청 → 워크스페이스 해석은 `index.ts` `resolveTenant()` 한 곳에서만 일어난다.

```
요청 도착
  │
  ├─ Authorization: Bearer stepd_live_…  있음
  │     → sha256 조회 → 폐기·정지·스코프 검사 → 라우트 화이트리스트 검사
  │     → scope = 그 키의 워크스페이스,  via = "api-key"
  │
  ├─ 세션 쿠키 있음
  │     → scope = 그 사용자의 워크스페이스,  via = "web"
  │
  └─ 둘 다 없음
        → AUTH_REQUIRED 켜짐이면 401 / 꺼짐이면 t_default 폴백

  ▼  셋 다 같은 출구
runWithTenant(ctx) → 그 안의 모든 DB 접근은 RLS가 막는다
```

**이게 설계의 중심이다.** 키 경로가 자체 필터를 갖기 시작하면 격리 로직이 두 벌이 되고
**한 벌은 반드시 샌다.** 키가 하는 일은 "누구 것인가"를 정하는 것까지고, 그 뒤는 세션과 완전히 같다.

### 공장 라우트는 익명 폴백을 허용하지 않는다

`/api/factory/*`는 **남의 YouTube 채널에 영상을 올릴 수 있는 표면**이다.
`AUTH_REQUIRED`가 꺼진 단일 테넌트 자세에서의 폴백이 여기선 곧 사고이므로,
API 키 또는 로그인 세션이 없으면 무조건 401이다(구 `x-factory-key`의 방어를 대체).

## 5. 워크스페이스 API 키 — 무엇이고 어떻게 안전한가

### 형태

```
stepd_live_<base64url 24바이트>      운영용
stepd_test_<…>                       테스트용
```

- DB에는 **sha256 해시와 접두 15자(`stepd_live_ab12`)만** 저장한다.
- **평문은 발급 응답에 딱 한 번** 나가고 끝이다. 다시 조회할 수 없다.
  → 저장하면 DB 유출이 곧 "남의 채널에 영상을 올릴 수 있는 권한"이 된다.
- 폐기는 행 삭제가 아니라 `revoked_at` 기록. 누가 언제 발급하고 폐기했는지가 남아야 한다.
- `last_used_at`은 **1분 스로틀**로 갱신한다(안 쓰는 키 회수용이라 분 단위면 충분).

### 스코프 6종

`media:write` · `media:read` · `search:read` · `factory:write` · `factory:read` · `billing:read`

표준 고객사 키 = 6종 전부. 모르는 스코프는 **에러가 아니라 무시**한다 —
오타 하나로 발급이 실패하면 운영자가 "스코프를 아예 안 주는 쪽"으로 도망가는데 그게 더 위험하다.
단, 전부 걸러져 비면 **키를 만들지 않는다**(아무것도 못 하는 키는 고객사가 권한 문제인지 장애인지 구분 못 한다).

### 라우트 화이트리스트 — 기본값이 "닫힘"

서버 라우트는 118개지만 그건 **세션을 가진 운영자**를 전제로 만든 것이다.
`api-keys.ts`의 `API_KEY_ROUTES`에 **명시적으로 올린 21개만** 열고 나머지는 전부 403이다.
새 라우트가 생겨도 기본값이 닫힘이다.

| 묶음 | 라우트 | 스코프 |
|---|---|---|
| 넣기 | `POST /api/media/upload-init` · `/finalize` · `/:id/analyze` | `media:write` |
| 가져가기 | `GET /api/media/:id/analysis` · `/transcript` · `/stream-url` · `/shorts` · `/clips` · `/thumb` · `/frame` · `/analysis/frames/:name` · `/thumbnails` | `media:read` |
| 찾기 | `GET /api/search` | `search:read` |
| 공장 | `POST /api/factory/videos` · `/ingest` · `/channels` · `/channels/connect-url` | `factory:write` |
| 공장 | `GET /api/factory/targets` · `/jobs/:id` · `/jobs/:id/performance` | `factory:read` |
| 잔액 | `GET /api/credits` | `billing:read` |

**결제·카드 등록·회사 관리는 열지 않는다.** 그건 사람이 화면에서 판단할 일이다(의도).

### 키가 거부되는 네 가지 — 이유를 구분해서 준다

```
알 수 없는 API 키입니다.            401   ← 해시 불일치
폐기된 API 키입니다.                401   ← revoked_at 있음
워크스페이스가 정지되었습니다.        401   ← 회사 status ≠ active
이 키에 허용된 권한이 없습니다.       401   ← 스코프 0개
이 키에 factory:write 권한이 없습니다. 403   ← 열려있는데 스코프 부족
API 키로 호출할 수 없는 경로입니다.    403   ← 화이트리스트 밖
크레딧 잔액이 없습니다.               402   ← 충전 필요
```

"401"만 주면 고객사가 키를 재발급받아도 같은 벽을 만난다.
특히 **403 두 종류를 구분**하는 게 중요하다 — "우리 키가 잘못됐나"와 "그 기능은 API에 없나"는 대응이 다르다.

> **회사 정지가 키까지 죽인다.** 세션만 끊고 키를 살려두면 미납 회사가 API로 계속 쓴다.

## 6. KT ENA 연동 — 실제 그림

### 구조

```
        KT ENA (고객사)                          STEPAI
 ┌──────────────────────────┐        ┌────────────────────────────────────┐
 │  AENA 백엔드              │        │  Cloud Run: stepd-server           │
 │  (ENA 자체 서비스)         │        │                                    │
 │                          │        │   resolveTenant()                  │
 │  env:                    │  HTTPS │     ├ Bearer 키 → ENA 워크스페이스   │
 │   STEPD_API_KEY=         │───────▶│     └ 세션 쿠키 → 사용자 워크스페이스 │
 │     stepd_live_…         │ Bearer │                ↓                   │
 └──────────────────────────┘        │        runWithTenant(ENA)          │
              │                      │                ↓                   │
              │                      │   ┌────────────────────────────┐   │
              │                      │   │  RLS: tenant_id = 'ENA'    │   │
              │                      │   └────────────────────────────┘   │
              │                      └────────────────────────────────────┘
              │                                       │
              │                                       ▼
              │                        ENA 워크스페이스 (= tenants 행 하나)
              │                        프로그램 · 영상 · 클립 · 채널 · 성과 · 크레딧
              │                                       ▲
              │                                       │ 같은 데이터
              │                      ┌────────────────────────────────────┐
              └─ 담당자가 브라우저로 ──▶│  stepd.stepai.kr  (세션 로그인)     │
                                     │  검수 · 편집 · 채택 · 배포 · 충전    │
                                     └────────────────────────────────────┘
```

**같은 워크스페이스에 두 입구가 붙는다.** AENA가 API로 만든 클립을 ENA 담당자가 웹에서 손보고 배포할 수 있다.
이게 "API만 파는 회사"와 우리를 가르는 지점이다.

### AENA 쪽이 부르는 순서

```
0. POST /api/factory/channels/connect-url   채널 주인이 동의 → refresh token 확보
1. GET  /api/factory/targets                배포 가능한 채널 확인 (canPublish + 사유)
2. POST /api/factory/videos                 { url, programId, title } → mediaId
3. POST /api/factory/ingest                 { sourceUrl, programId, targets, policy, idempotencyKey }
                                            → 202 { jobId }
4. GET  /api/factory/jobs/:id               60초 주기 폴링
5. GET  /api/media/:id/shorts · /clips · /analysis · /transcript    산출물 회수
6. GET  /api/factory/jobs/:id/performance   성과
```

공장 상태 진행:

```
queued → ingesting → analyzing(실측 16분) → adopting → rendering → publishing → publicizing → done
                                                                    hold(일일 상한) · failed
```

`hold`는 **실패가 아니다** — 일일 상한에 걸린 보류다. 고객사가 이걸 실패로 읽지 않게 문서에 못박아 뒀다.
업로드 직후 `hasMetrics:false`도 정상이다(지표는 채널 동기화 주기에 채워진다).

### 왜 상태기계인가

`content.analyze`는 실측 16분이다. 오케스트레이터가 그동안 워커를 붙잡고 기다리면
drain 모드에서 잡 하나가 워커를 통째로 점유한다. 그래서 **한 걸음 전진하고 재큐**한다.

### 전자동의 안전장치 4개

승인 절차가 아니라 **사고 시 손을 뗄 수 있는 장치**다.

| 장치 | env / 파라미터 | 기본 | 막는 사고 |
|---|---|---|---|
| 킬 스위치 | `FACTORY_ENABLED` | **off** | 잘못된 env의 실패 방향이 "안 돌아감"이지 "실수로 배포됨"이 아니게 |
| 드라이런 | `policy.dryRun` | false | 클립까지 만들고 업로드는 안 함. **첫 연동은 이걸로 검증** |
| 일일 상한 | `FACTORY_DAILY_CAP` | 5/프로그램 | 파이프라인 버그로 같은 영상이 20번 올라가는 사고 |
| 유예 공개 | `FACTORY_PUBLICIZE_DELAY_MIN` | 10분 | private 업로드 후 유예. 그 사이가 되돌릴 시간 |

시간당 ingest 상한은 `FACTORY_HOURLY_LIMIT`(기본 20, 워크스페이스당).
복귀 URL은 `FACTORY_RETURN_ORIGINS` allowlist에 등록된 오리진만 — 오픈 리다이렉트 방지.

### 배포 채널 현황 — YouTube만 실동작

| 채널 | 상태 |
|---|---|
| **YouTube** | 실업로드 구현됨 · `upload-gate.ts` 3중 방어로 기본 OFF |

## 7. 과금 — 선불 크레딧 단일

### 규칙

```
크레딧 1개 = 분석 1분
청구 분     = ceil(media.duration_sec / 60)        61분 영상 = 62크레딧
```

- 잔액 부족이면 분석이 **시작조차 안 된다**(402). 돌리고 나서 "잔액이 없었네"는 원가를 이미 쓴 뒤다.
- 원장은 **append-only**. 마이그레이션 0024의 트리거가 UPDATE/DELETE를 막는다.
  정정도 반대 부호 행을 하나 더 쌓는 것이지 지우는 게 아니다.
- 잔액은 **원장 합계**다. 캐시하지 않는다 — 어긋난 잔액은 조용히 틀린 채로 굴러간다.
- 잔액이 음수로 내려가는 것은 **막지 않는다.** 이미 쓴 분석을 없던 일로 만들 수 없고,
  음수 잔액은 "받을 돈이 있다"는 사실 그대로다. 0으로 누르면 그 사실이 사라진다.
- 멱등: 충전은 결제 하나당 한 번(`topup:<paymentId>`), 사용은 미디어 하나당 한 번(`usage:<mediaId>`).
  웹훅은 재전송되고 워커는 재시도한다.
- 운영자 수동 조정은 `grant` · `adjust` · `refund` 만. **`topup`과 `usage`는 손으로 못 쓴다** —
  전자는 매출이 부풀고 후자는 원가 집계가 어긋난다. 1회 한도 100,000.

### 가격은 아직 미정 — 그리고 원가 기준이 바뀌었다

`CREDIT_PRICE_KRW`는 env로 받는다. **코드에 숫자를 박지 않았다.**

> ⚠️ **가격 결정 전에 반드시 볼 것.** `billing-portone-plan.md`가 근거로 삼은 원가는
> **분당 ₩4.9**(58.6분 회차 = ₩285)인데, 이 값은 `core/retry.py`의 Gemini 단가표가
> 2.0 Flash 단가를 2.5 Flash 라벨에 붙여둔 오류에서 나왔다.
> usage.json 실측 토큰으로 재산출하면 **회차당 ₩994 = 분당 약 ₩17**이다.
>
> **원가가 3.5배다.** 마진 배수를 원가에 곱해 가격을 정하는 구조이므로,
> 옛 숫자로 견적을 내면 ENA 계약이 그대로 역마진이 된다.
> 상세: `docs/ops/cost-and-dependencies.md`

### 결제 수단

PortOne 일반결제(선불 충전). 구독·빌링키가 아니다.
카드 등록(빌링키)·충전은 **웹 화면에서 세션으로만** 한다 — API 키로는 `GET /api/credits` 조회만 가능하다(의도).

브라우저를 믿지 않는다: 결제창이 성공을 알려도 크레딧을 올리지 않고,
PortOne에 조회해 금액·상태가 우리가 만든 주문과 일치할 때만 올린다.

## 8. 운영자 콘솔 (`admin.stepd.stepai.kr`)

**STEPAI 운영자 전용**(superadmin 세션 필수). 고객사는 여기 안 들어온다.

회사 상세가 6탭이다:

| 탭 | 내용 |
|---|---|
| 개요 | 상태·규모·조치가 필요한 잡 |
| 성과 | 채널별 조회수·시청시간·순구독자·예상수익 |
| 결제·크레딧 | 잔액 · 원장 · 수동 조정 · 최근 결제 |
| 멤버 | 계정 추가·역할·비밀번호 재설정·삭제 |
| **API 키** | 발급(평문 1회 노출) · 접두사 · 마지막 사용 · 폐기 |
| 운영 이력 | 감사 로그 타임라인 |

**읽기는 사유 없이, 쓰기는 사유 강제.** 운영자가 매번 사유를 적어야 하면 지원이 안 굴러가고,
쓰기는 남의 데이터를 바꾸는 일이라 근거가 남아야 한다.

회사 개설은 **회사 + 첫 owner 초대 + 초기 크레딧을 한 트랜잭션**으로 묶었다.
예전엔 따로여서 "아무도 못 들어가는 회사"가 남았다.

회사 id는 **그냥 순번**(`1`·`2`·`3`)이다. 사람에게 의미 있는 건 이름이지 id가 아니다.
(예전 `t_` + 이름 슬러그 방식은 한글 이름이 전부 `t__`로 유도돼 두 번째 한글 회사부터 409였다.)

## 11. 팀이 자주 받을 질문

**Q. 고객사가 API 키를 자기 웹 프론트에 넣으면?**
유출이다. 키가 있으면 **남이 그 워크스페이스 채널에 영상을 올릴 수 있다.**
이미지 에셋을 고객사 화면에 보여줄 때도 **고객사 서버가 프록시**하게 한다.

**Q. 키를 잃어버렸다고 하면?**
평문은 복구할 수 없다(sha256만 저장). 기존 키 폐기 후 **재발급**한다.

**Q. A사 키로 B사 데이터를 볼 수 있나?**
없다. 키가 세우는 건 `app.tenant_id` 뿐이고, 그 뒤는 RLS가 행 자체를 숨긴다.
`rls-access.test.ts`가 이 경로를 잠그고 있다.

**Q. API로 넣은 영상이 웹 화면에도 보이나?**
보인다. 그게 이 설계의 판매 포인트다 — 같은 워크스페이스, 같은 데이터.

**Q. 미납 회사를 어떻게 막나?**
회사 `status`를 `suspended`로. 세션 파기 + 로그인 거부 + **API 키 거부** + 잡 차단이 같이 걸린다.

**Q. 크레딧 단가는 얼마로 부르나?**
아직 미정이다. **§7의 원가 정정(분당 ₩4.9 → 약 ₩17)을 반영한 뒤** 마진 배수를 얹어 정한다.

**Q. 60분 영상 하나가 얼마나 걸리나?**
분석만 실측 16분. ingest→published 전체는 대략 25~35분 예상(측정 후 확정).
SLA로 약속하기 전에 실측이 필요하다.

## 12. 아직 정하지 않은 것

| 항목 | 왜 아직인가 |
|---|---|
| **크레딧 단가** | 원가 재산출 반영 후 마진 배수는 사업 판단 |
| **최소 커밋 / 볼륨 티어** | 인프라가 고정비라 저사용 달 역마진 방지 장치가 필요한데, 계약 형태가 안 정해짐 |

| **웹훅 재전송·dead-letter** | 웹훅 자체가 후순위(폴링으로 시작) |
| **재분석 과금 기준** | 우리 귀책 실패는 무료 / 사용자 의도 재분석은 재과금 — 판정 로직 미배선 |
