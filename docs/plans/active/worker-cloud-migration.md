# 워커 클라우드 이전 — 비용·성능 조사

> 2026-08-07. 사용자 요청: "로컬에서 워커 안 돌리고 모든 걸 클라우드로. 비용 및 어떻게
> 하는 게 비용적·성능적으로 괜찮은지 조사."
>
> 아래 잡 통계는 프로덕션 `job_queue` 실측이다. **GCP 단가는 공개 리스트 가격 기준의
> 추정이며 청구서 대조 전이다** — 자릿수 판단에는 충분하지만 계약서로 쓰면 안 된다.

## 1. 지금 워커가 실제로 하는 일

프로덕션 `job_queue` 누적 (2026-08-07 기준, `status='done'`):

| 잡 | 건수 | 성격 |
|---|---:|---|
| `video.comments` | 36,438 | YouTube API 호출 + DB 쓰기 |
| `video.analyze` | 16,261 | YouTube Analytics API + DB |
| `channel.analyze` | 13,902 | 채널 동기화 + 애널리틱스 |
| `video.hotwatch` | 13,611 | 48h 시간별 스냅샷 (자기 재큐) |
| `match.align` | 277 | 오디오 정렬 (CPU 중간) |
| `youtube.download` | 47 | yt-dlp → GCS (네트워크) |
| **`content.analyze`** | **12** | **core 파이프라인 (평균 69.1분)** |
| `match.segment` / `match.learn` | 4 | Lab |

**결론이 여기서 거의 나온다. 워크로드가 두 종류로 완전히 갈린다.**

**A. 고빈도 경량 잡 — 전체의 99.98%**
YouTube API 응답을 기다리고 DB에 쓰는 게 전부다. CPU는 거의 안 쓰고 대부분 IO 대기다.
15분마다 sweep(`TICK_INTERVAL_MS`)이 돌며 채널을 큐잉하고, idle 시 5초 폴링(`IDLE_POLL_MS`)한다.
**상시 프로세스가 필요한 이유는 폴링 하나뿐이다.**

**B. 저빈도 중량 잡 — 12건**
`content.analyze` 평균 69.1분(큐잉→완료). 60분 회차 API 비용 ~₩620
(⚠️ 2026-08-07 정정: 이 안의 Soniox ₩270 은 과대추정이었다 — 실제 $0.10/시간 ≈ ₩135).
전부 2026-07에 몰려 있고 8월엔 0건 — 아직 상시 운영 부하가 아니다.

## 2. B가 CPU만으로 되는가 (GPU 필요 여부)

이전(2026-07 이전)엔 GPU가 필요했지만 지금은 아니다:

| 스테이지 | 예전 | 지금 |
|---|---|---|
| STT | 로컬 whisper (GPU) | **Soniox API** (`STT_PROVIDER=soniox`) |
| Vision (chyron·scene_type·beat_annot) | — | **Vertex Gemini API** |
| 임베딩 | — | **Vertex text-multilingual-embedding-002** |
| faces (InSightFace) | GPU | **`RUN_FACES` 기본 off** |
| PPL | GPU 프레임 추출 | **`RUN_PPL=0` 기본 off** |
| shot boundary | ffmpeg scene 필터 | 동일 (CPU) |
| GEBD | GPU | **이미 별도 spot T4 VM** (`gebd.detect` 전용 lane) |

**남는 로컬 연산은 ffmpeg(디코딩·프레임 추출·오디오 1패스)뿐이고 전부 CPU다.**
즉 메인 워커는 **CPU 전용으로 클라우드에 올릴 수 있다.** GPU가 필요한 GEBD는 이미 분리돼 있고,
`RUN_FACES=1`을 켜야 하는 날이 오면 그때만 GPU 경로를 따로 붙이면 된다.

## 3. 선택지

### 옵션 1 — Cloud Run Jobs (권장)

잡 하나 = 실행 하나. 서버가 큐잉할 때 Jobs를 트리거하고, 끝나면 컨테이너가 사라진다.

- 최대 실행시간 24시간 → 69분 파이프라인 수용
- **실행 중에만 과금.** idle 비용 0
- 이미 쓰는 이미지(ffmpeg 포함)를 그대로 재사용 — 새 인프라 학습 없음
- 동시 실행 = 병렬 처리. 회차 3편이 와도 3배 기다리지 않는다

**A(경량 잡)는 Cloud Scheduler + Cloud Run Job으로 15분마다 배치 처리**한다. 5초 폴링을
없애는 게 핵심 — 상시 프로세스가 사라진다.

### 옵션 2 — GCE Spot VM (상시)

지금 로컬 pm2 구조를 그대로 옮기는 것. 코드 변경이 가장 적다.

- Spot은 정가의 60~91% 할인, 대신 **언제든 선점(preempt)될 수 있다**
- 69분 잡 중간에 선점되면 재시도인데, `content.analyze`는 `maxAttempts=2`이고
  체크포인트가 있어 복구는 된다. 다만 API 비용은 이미 쓴 뒤다
- idle 시간에도 과금 (STOP 스크립트를 붙이면 완화)

### 옵션 3 — GKE / Batch

지금 규모(월 12건 + 폴링)에 클러스터 운영비와 복잡도가 정당화되지 않는다. 제외.

### 옵션 4 — 현행 유지 (로컬 pm2)

전기료 외 직접비 0. 대신 **PC가 꺼지면 파이프라인이 멈춘다.** 실제로 어제 Docker가 내려가며
로컬 DB가 죽어 검색이 500을 냈고, pm2 프록시가 중복 기동으로 573회 재시작한 이력이 있다.
운영 서비스의 SPOF가 개인 PC라는 게 가장 큰 비용이다(금액이 아니라 리스크).

## 4. 비용 추정

> 단가는 us-central1 리스트 가격 추정. **청구서 대조 필요.**

### 전제

- `content.analyze` 월 12건 × 69분 ≈ **14 CPU-시간/월** (2 vCPU 기준 28 vCPU-시간)
- 경량 잡: 15분마다 배치 1회 = 월 2,880회 × 평균 20초 ≈ **16 CPU-시간/월**
- 네트워크 egress는 GCS 내부 전송이 대부분이라 무시 가능

### 옵션 1 (Cloud Run Jobs, CPU 2 / 메모리 4Gi)

| 항목 | 계산 | 월 |
|---|---|---|
| 중량 잡 | 28 vCPU-h + 56 GiB-h | ~$2 |
| 경량 잡 배치 | 32 vCPU-h + 64 GiB-h | ~$2.5 |
| **소계** | | **~$5 (₩7천)** |

부하가 10배로 늘어도 ~$50 선. **사용량 비례라 초기엔 사실상 공짜다.**

### 옵션 2 (GCE Spot, e2-standard-4 상시)

| 항목 | 월 |
|---|---|
| e2-standard-4 spot 상시 | ~$25~30 |
| 부팅 디스크 50GB | ~$2 |
| **소계** | **~$30 (₩4만)** |

idle이 대부분인데 상시 과금이라 **옵션 1보다 6배**다. 다만 코드 변경이 거의 없다.

### 참고 — 지금 이미 나가는 돈

API 비용이 인프라보다 훨씬 크다. 회차당 ~₩485 × 12건 = **월 ~₩5,800**.
**인프라를 어느 쪽으로 고르든 API 비용에 묻힌다.** 이 결정은 금액보다 **안정성·운영 편의**로
판단하는 게 맞다.

## 5. 권장안

**Cloud Run Jobs로 간다. 단, 한 번에 다 옮기지 않는다.**

| 단계 | 옮기는 것 | 이유 |
|---|---|---|
| 1 | 경량 잡 (channel/video.*) | 99.98%를 차지하면서 가장 단순. 폴링 제거 효과가 즉시 |
| 2 | `content.analyze` | 69분 잡. 체크포인트가 이미 있어 재시도 안전 |
| 3 | `thumbnail.*` | 방금 만든 것. 이미 CLI 스폰 구조라 이식이 쉽다 |
| 4 | `match.*` (Lab) | 사용 빈도 낮음. 마지막 |

GEBD(`gebd.detect`)는 **지금 구조 유지**. 이미 spot T4 + idle STOP으로 월 $6~10 설계다.

### 이행에 필요한 코드 변경

1. **워커 루프 → 잡 1건 실행 모드.** `worker.ts`가 지금은 무한 폴링인데,
   `--once` 모드(큐에서 하나 claim → 처리 → 종료)를 추가하면 Cloud Run Job이 그대로 쓴다.
2. **큐잉 시 Job 트리거.** `enqueue()` 뒤에 Cloud Run Jobs `run` 호출. 또는 Scheduler가
   1분마다 깨워 pending을 소진하는 단순한 방식(트리거 배관 불필요, 최대 1분 지연).
3. **에셋 경로.** 이미 `STEPD_STORAGE_DIR`/GCS 양쪽을 타므로 추가 작업 없음.
   썸네일은 `thumbnail-assets.ts`가 GCS pull/push를 한다.
4. **비밀값.** `.env.worker`에 있는 것들(`OPENAI_API_KEY`·`SONIOX_API_KEY`·`HF_TOKEN` 등)을
   Secret Manager로. 지금 Cloud Run이 쓰는 방식과 동일.

### 성능 측면에서 달라지는 것

- **좋아짐**: 회차 여러 편이 동시에 와도 병렬 실행(지금은 로컬 1대 직렬).
  PC 상태와 무관하게 돎.
- **나빠짐**: 콜드 스타트(수 초~수십 초). 69분 잡에는 무의미하고, 경량 잡은 배치라 무관.
- **주의**: Cloud Run Jobs는 **로컬 디스크가 tmpfs(메모리)**다. 60분 영상을 `/tmp`에
  받으면 메모리를 그만큼 먹는다. CLAUDE.md에 이미 경고된 함정이고, 메모리를 넉넉히 잡거나
  스트리밍 처리로 가야 한다. **이게 이번 이전의 가장 큰 기술 리스크다.**

## 6. 남은 확인 사항

- [ ] `content.analyze`의 **실제 피크 메모리**. 60분 영상 ffmpeg 처리 시 tmpfs 사용량을 재야
      Cloud Run Job 메모리(4Gi? 8Gi? 16Gi?)를 정할 수 있다. 이 값이 비용을 좌우한다.
- [ ] 리스트 가격 → 실제 청구서 대조. 위 $5는 추정이다.
- [ ] `RUN_FACES=1`을 켤 계획이 있는지. 켜면 GPU 경로가 다시 필요하고 그림이 바뀐다.
- [ ] 경량 잡의 실제 평균 실행시간(위 20초는 **가정**). `job_queue`에 시작시각 컬럼이 없고,
      `lockedat`도 완료 시 비워져서 **현재 스키마로는 측정 자체가 불가능하다**(실제로 조회해보니
      전 기간 통틀어 2건만 값이 남아 있고 그마저 0초). 실행시간을 근거로 비용을 확정하려면
      `startedat`/`finishedat` 컬럼을 먼저 추가해야 한다. 이건 이전 여부와 무관하게
      운영 가시성 문제이기도 하다.
