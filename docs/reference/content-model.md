# STEP D 콘텐츠 모델 — 롱폼 → 클립 → 숏폼·하이라이트

> **상태: 제품 개념 정본 · 2026-07-27**  
> 이 문서는 STEP D의 화면 구조, 추천·편집 파이프라인, 데이터 모델이 따라야 할 콘텐츠 계층을 정의한다.
> 용어가 코드의 기존 `shortform`·`clip`·`highlight`와 충돌할 때는 이 문서의 **제품 의미**를 우선으로 판단하고,
> 코드 정리는 별도 마이그레이션으로 수행한다.

## 한 문장 정의

**롱폼을 분석해 완결된 클립을 만들고, 클립을 재료로 플랫폼용 숏폼과 여러 클립을 엮은 하이라이트를 만든다.**

```text
롱폼(원본)
  └── 클립(완결된 기본 편집 단위)
        ├── 숏폼(플랫폼별 세로형 파생본)
        │     ├── YouTube Shorts
        │     ├── Instagram Reels
        │     ├── TikTok
        │     └── Facebook Reels
        └── 하이라이트(여러 클립을 선택·연결한 중간 길이 결과물)
```

---

## 1. 콘텐츠 유형

| 유형 | 정의 | 길이·비율 | 생성 방식 | 역할 |
|---|---|---|---|---|
| **롱폼** | 원본 또는 전체 내용을 담은 소스 영상 | 10분~수시간 · 자유 | 업로드·연동 | 모든 파생 콘텐츠의 기준 |
| **클립** | 롱폼에서 추출한 하나의 완결 장면·이야기 단위 | 수초~수분 · 제한 없음 | AI 분석 후 운영자가 채택 | 가장 기본적인 편집 재료 |
| **숏폼** | SNS 소비를 위한 짧은 파생 콘텐츠의 상위 개념 | 보통 15초~3분 · 주로 9:16 | 클립 재프레이밍·자막·편집 | 플랫폼별 빠른 소비 |
| **쇼츠** | YouTube Shorts용 숏폼 | 최대 3분 · 9:16 | 클립을 YouTube 규격으로 제작 | YouTube Shorts 피드 배포 |
| **하이라이트** | 여러 핵심 클립을 선택·연결한 중간 길이 영상 | 보통 1~10분, 필요 시 약 20분 · 자유 | 클립 순서 구성·전환·편집 | 본편 핵심 압축 및 본편 유도 |

### 롱폼 (Long-form)

- TV 방송 한 회, 유튜브 본편, 강의 전체, 인터뷰 전체처럼 **전체 맥락**을 가진 원본이다.
- 롱폼 자체를 재단하거나 재구성한 결과물은 롱폼이 아니라 파생 콘텐츠로 관리한다.

### 클립 (Clip) — 제품의 기본 단위

- 롱폼의 특정 구간에서 **시작·전개·반응·마무리가 가능한 한 덩어리**를 보존한 영상이다.
- 길이, 가로·세로 비율, 배포 플랫폼으로 클립의 정체성을 제한하지 않는다.
- 하나의 클립은 여러 숏폼의 소스가 될 수 있고, 여러 클립은 하나의 하이라이트가 될 수 있다.
- 운영자가 검토·채택·편집·재사용하는 기본 객체는 클립이다.

### 숏폼 (Short-form)과 쇼츠 (YouTube Shorts)

- **숏폼**은 Shorts·Reels·TikTok 등을 포괄하는 상위 개념이다.
- **쇼츠**는 YouTube Shorts라는 특정 플랫폼용 숏폼이다.
- 숏폼은 클립을 그대로 업로드하는 것이 아니라 플랫폼 요구에 맞게 다음을 적용한 **파생본**이다.
  - 9:16 리프레임 또는 크롭
  - 자막
  - 인물 확대·포커스 조정
  - 플랫폼별 길이·안전 영역·메타데이터
- 일반 운영 기준은 15초~3분이며, 특정 배포 채널의 최종 규격은 그 채널 preset이 결정한다.

### 하이라이트 (Highlight)

- 하이라이트는 단일 구간의 다른 이름이 아니다.
- 여러 클립을 고르고 순서를 구성하며, 필요하면 전환·자막·내레이션을 더한 **조합 결과물**이다.
- 경기 주요 장면 모음, 예능 베스트 모음, 인터뷰 핵심 요약이 대표 사례다.

## 2. beat와 clip의 관계

### beat는 분석의 퍼즐 조각, clip은 제품의 기본 객체

| 구분 | beat | clip |
|---|---|---|
| 위치 | AI 분석·서사 타임라인 내부 | 운영자 화면·편집·배포의 제품 객체 |
| 의미 | 장면·발화·반응을 포함한 완결 후보 경계 | 채택되어 재사용 가능한 실제 편집 단위 |
| 길이 | **상한·하한으로 자르지 않음** | beat 경계를 보존해 생성하며, 파생본에서만 플랫폼 규격 적용 |
| 역할 | 클립을 만들기 위한 의미적 원재료 | 숏폼·하이라이트의 재료 |

**핵심 원칙:** beat는 이미 AI가 찾아낸 의미 단위이므로, 추천 단계에서 길이 규칙으로 다시 자르지 않는다.  
기존에 `40~60초` 또는 `90초`로 beat 내부를 재단해 셋업·리액션·마무리가 손실된 문제를 금지한다.

```text
롱폼 분석
  → beat 탐지 (원래 경계 보존)
  → clip 후보 생성 (beat 1개 = clip 후보 1개)
  → 운영자 채택
  → clip 확정
  → 숏폼 또는 하이라이트 파생
```

> 길이 규칙은 **클립 후보를 훼손하는 추천 단계가 아니라**, 숏폼·쇼츠 같은 파생본의 플랫폼별 렌더 단계에서 적용한다.

## 3. 생성 흐름

```text
[롱폼 업로드·연동]
        │
        ▼
[AI 분석]
  STT · 장면분할 · 인물/시각 분석 · 서사 beat 탐지
        │
        ▼
[클립 후보]
  beat 경계를 보존한 완결 단위
        │
        ├── 운영자 채택 → [클립 라이브러리]
        │                    │
        │                    ├── [숏폼 제작]
        │                    │      9:16 리프레임 · 자막 · 인물 포커스
        │                    │      → Shorts / Reels / TikTok / Facebook Reels
        │                    │
        │                    └── [하이라이트 제작]
        │                           여러 클립 선택 · 순서 구성 · 연결
        │                           → 주요 장면 / 압축본
        │
        └── 운영자 거절 또는 보류
```

## 4. UI 정보 구조

UI도 이 계층을 그대로 보여준다. 추천 결과를 곧바로 “쇼츠”로 부르지 않는다.

### A. 회차 상세: 롱폼과 클립 후보

```text
회차 상세
  ├── 롱폼 플레이어·분석 타임라인
  ├── beat / 클립 후보 보드
  │     ├── 원본 구간
  │     ├── 서사·인물·대사 근거
  │     ├── 길이·완결성
  │     └── 채택 → 클립 라이브러리
  └── 분석 결과
```

### B. 클립 라이브러리: 제품의 중심 화면

```text
클립 라이브러리
  ├── 클립 원본 구간·상태·태그
  ├── 클립 편집
  ├── 숏폼 파생본
  │     ├── Shorts
  │     ├── Reels
  │     └── TikTok
  └── 하이라이트 편성에 추가
```

### C. 하이라이트 빌더

```text
하이라이트 빌더
  ├── 클립 선택
  ├── 순서·전환 구성
  ├── 전체 길이 미리보기
  └── 렌더·배포
```

### UI 원칙

1. **클립이 기본 객체다.** 모든 추천·편집·배포 추적은 클립에서 시작한다.
2. **숏폼은 클립의 파생본이다.** 9:16, 자막, 플랫폼 preset은 원본 클립을 훼손하지 않는다.
3. **하이라이트는 클립의 조합이다.** 단일 클립을 하이라이트라고 부르지 않는다.
4. **beat는 운영자에게 근거로 보일 수 있지만 내부 분석 단위다.** 채택 이후의 제품 객체는 클립이다.

## 5. 구현 정렬 원칙

| 영역 | 따라야 할 원칙 |
|---|---|
| AI 추천 | beat 경계를 보존해 클립 후보를 만든다. 길이로 beat를 재단하지 않는다. |
| 클립 채택 | 추천 후보를 클립 엔터티로 승격하고 원본 구간·근거·버전을 보존한다. |
| 숏폼 렌더 | 확정된 클립을 입력으로 9:16·자막·플랫폼 규격을 적용한다. |
| 하이라이트 렌더 | 여러 확정 클립의 순서·전환을 저장한 composition을 입력으로 렌더한다. |
| 썸네일 | 클립 또는 그 플랫폼 파생본을 기준으로 계획 → 레이어 생성 → 합성한다. |
| UI 네이밍 | “쇼츠 추천” 대신 “클립 후보”, “쇼츠 제작”처럼 후보·클립·파생본 단계를 구분해 표기한다. |

## 6. 현재 코드와의 정렬 과제

현재 파이프라인에는 과거 의미의 `shortform`·`clip` 구분이 남아 있다. 제품 개념을 바꾸는 이 문서만으로 기존 데이터나 UI 라벨을 자동 변환하지 않는다.

다음 구현 작업은 이 순서로 진행한다.

1. AI 추천 결과를 `클립 후보` 중심 계약으로 통일한다.
2. beat 1개를 훼손 없이 clip 후보로 승격한다.
3. 채택된 clip에서 숏폼 파생 render job을 생성한다.
4. 여러 clip을 참조하는 highlight composition과 renderer를 추가한다.
5. UI의 추천 보드·클립 라이브러리·하이라이트 빌더를 위 정보 구조에 맞춘다.
