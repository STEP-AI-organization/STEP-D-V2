STEP D — 워크스페이스 판매 + 고객사 API 연결

B2B SaaS 구조 한 장 요약 · 기준 커밋 d8ba693 · 정본 문서 docs/plans/active/b2b-workspace-strategy.md

STEP D는 회사 단위 워크스페이스를 판다. 워크스페이스 하나 안에서 프로그램·영상·클립·배포채널·성과·크레딧이 전부 격리된다. 고객사가 들어오는 입구는 둘인데, 둘 다 같은 워크스페이스로 떨어진다.

  ① 사람이 화면에서       stepd.stepai.kr 로그인  →  업로드·검수·채택·배포
  ② 고객사 시스템이 API로  Authorization: Bearer stepd_live_…

                          ↓  둘 다 같은 출구

              같은 워크스페이스 · 같은 데이터 · 같은 크레딧 원장
판매 논리. API는 별도 상품이 아니라 워크스페이스의 두 번째 입구다. AENA가 API로 만든 클립을 ENA 담당자가 웹에서 그대로 이어서 손볼 수 있다 — "API만 파는 회사"와 갈리는 지점.

02 격리 — 3중, 전부 fail-closed

"실수하면 유출"이 아니라 "실수하면 안 보임"이 되도록 방향을 잡았다.

겹 1 · DB가 막는다

23개 표에 RLS. 커넥션마다 app.tenant_id를 심고 정책이 행을 숨긴다. 값이 없으면 0행.

FORCE ROW LEVEL SECURITY 필수 — ENABLE만 걸면 테이블 소유자가 우회한다.

겹 2 · 코드가 던진다

tenant.ts의 AsyncLocalStorage. 스코프가 없으면 폴백이 아니라 throw.

폴백이 있으면 배선을 빼먹어도 화면이 멀쩡히 뜨고, 외부 방송사를 받는 순간 샌다.

겹 3 · 서버가 안 뜬다

워크스페이스 2개 이상 + AUTH_REQUIRED off → 전 라우트 503.

사람이 기억하는 데 기대지 않는다.

03 워크스페이스 API 키

형태stepd_live_… / stepd_test_…
저장sha256 + 접두 15자만. 평문은 발급 응답에 1회, 재조회 불가
폐기행 삭제 아님 — revoked_at 기록 (발급·폐기 이력 보존)
스코프media:write / media:read / search:read / factory:write / factory:read / billing:read
라우트서버 118개 중 화이트리스트 21개만 개방. 새 라우트 기본값 = 닫힘
미개방결제·카드 등록·회사 관리 — 사람이 화면에서 판단할 일

거부 응답을 구분해서 준다

401  알 수 없는 API 키입니다.
401  폐기된 API 키입니다.
401  워크스페이스가 정지되었습니다.
401  이 키에 허용된 권한이 없습니다.
403  이 키에 factory:write 권한이 없습니다.
403  API 키로 호출할 수 없는 경로입니다.
402  크레딧 잔액이 없습니다.

"401"만 주면 고객사가 재발급받아도 같은 벽을 만난다. 403 두 종류 구분이 특히 중요 — "우리 키가 잘못됐나"와 "그 기능이 API에 없나"는 대응이 다르다.

회사 정지가 키까지 죽인다. 세션만 끊고 키를 살려두면 미납 회사가 API로 계속 쓴다. status ≠ active면 세션 파기 + 로그인 거부 + 키 거부 + 잡 차단이 같이 걸린다.

⚠️ 가격 결정 전 필독 — 원가 기준이 바뀌었다.
기존 계획서의 근거 원가는 분당 ₩4.9(58.6분 회차 = ₩285)인데, 이 값은 core/retry.py의 단가표가 Gemini 2.0 Flash 단가를 2.5 Flash 라벨에 붙여둔 오류에서 나왔다. usage.json 실측 토큰으로 재산출하면 회차당 ₩994 = 분당 약 ₩17 — 3.5배다.
마진 배수를 원가에 곱해 가격을 정하는 구조이므로, 옛 숫자로 견적을 내면 ENA 계약이 그대로 역마진이 된다. 상세: docs/ops/cost-and-dependencies.md

결제는 PortOne 일반결제(선불 충전). 구독·빌링키가 아니다. 카드 등록·충전은 웹 세션에서만 — API 키로는 GET /api/credits 조회만. 브라우저를 믿지 않는다: 결제창이 성공을 알려도 PortOne에 조회해 금액·상태가 일치할 때만 크레딧을 올린다.

05 전자동의 안전장치 4개

승인 절차가 아니라 사고 시 손을 뗄 수 있는 장치다.

장치env / 파라미터기본막는 사고
킬 스위치FACTORY_ENABLEDoff잘못된 env의 실패 방향이 "안 돌아감"이지 "실수로 배포됨"이 아니게
드라이런policy.dryRunfalse클립까지 만들고 업로드 안 함 — 첫 연동은 이걸로 검증
일일 상한FACTORY_DAILY_CAP5 / 프로그램버그로 같은 영상이 20번 올라가는 사고
유예 공개FACTORY_PUBLICIZE_DELAY_MIN10분private 업로드 후 유예 — 그 사이가 되돌릴 시간

배포 채널은 YouTube만 실동작. Meta·TikTok은 앱 심사 대기(일정을 우리가 못 정함), 네이버는 한국 IP가 필요해 사무실 상시 PC 전용. ENA 제안 시 YouTube로 한정해서 말할 것.

06 진행 상황

0. 회사 정지 실효화완료
1. 죽은 과금 코드 정리 (크레딧 단일)완료
2. 회사 온보딩 원자화완료
3. 워크스페이스 API 키완료
4. 어드민 회사 중심 재구성 (6탭)완료
5. 큐 공정성 (회사별 라운드로빈)완료
factory → 워크스페이스 키 + 크레딧 게이트완료
ENA 워크스페이스 개설 · 키 발급 · 스모크다음

07 ENA 온보딩 체크리스트

순서가 중요하다. env(1번)를 건너뛰고 워크스페이스를 만들면 AUTH_REQUIRED 검사에 걸려 서버가 503으로 죽는다. 프로그램·채널(4번)을 건너뛰고 키를 주면 공장이 programId가 없어 404를 낸다.
  1. 프로덕션 env 선행 확인 — AUTH_REQUIRED=1 · CREDIT_PRICE_KRW · FACTORY_ENABLED=1 · FACTORY_RETURN_ORIGINS에 AENA 오리진 · PortOne 키 4종 · YOUTUBE_UPLOAD_ENABLED 시점 결정
  2. 회사 개설 — admin 콘솔: 이름 KT ENA · kind api · owner 이메일 · 초기 테스트 크레딧 (한 트랜잭션)
  3. 결제 수단 — owner 세션으로 웹 로그인 → 카드 등록 → 충전 (API 키로는 불가, 의도)
  4. 프로그램·채널 준비 — ENA 워크스페이스 안에서 프로그램 생성(캐스트 등록 포함) + YouTube 채널 연결(게시 모드)
  5. 키 발급 — 회사 상세 → API 키 탭 → 스코프 6종 → 평문 1회 노출 → 보안 채널로 AENA 서버 env에 전달
  6. 스모크 — policy.dryRun=true ingest 1건 완주 확인 후 실배포 전환

⚠️ 사내 t_default(STEPAI) 워크스페이스의 채널·프로그램은 ENA와 무관하다. ENA 것은 ENA 워크스페이스 안에 새로 만든다.

08 아직 정하지 않은 것

항목왜 아직인가
크레딧 단가원가 재산출 반영 후 마진 배수는 사업 판단
최소 커밋 / 볼륨 티어인프라가 고정비라 저사용 달 역마진 방지 장치가 필요한데 계약 형태 미정
SLAingest→published 목표 시간. 분석만 실측 16분, 전체 25~35분 예상 — 측정 후 확정
웹훅 재전송·dead-letter웹훅 자체가 후순위(폴링으로 시작)
재분석 과금 기준우리 귀책 실패는 무료 / 사용자 의도 재분석은 재과금 — 판정 로직 미배선
