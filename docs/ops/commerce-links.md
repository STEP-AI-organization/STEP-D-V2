# 커머스 제휴 링크 — 쿠팡파트너스 파이프라인

> 실측·배포 기준 **2026-08-27**. 근거·실험 기록은 [research/commerce-product-matching-probe-2026-08.md](../research/commerce-product-matching-probe-2026-08.md),
> 수익 모델은 [research/commerce-revenue-model-2026-08.md](../research/commerce-revenue-model-2026-08.md).
> 이 문서는 **지금 프로덕션에서 어떻게 돌고, 어떻게 운영하나** 하나만 다룬다.

## 0. 왜 있는가

편집자에게 쇼츠 발행은 이미 일이다. 그 위에 "상품 찾기 → 링크 발급 → 대가성 문구 붙이기"를
얹으면 **아무도 안 한다.** 실제로 아무도 안 해서 이 수익은 0원이 아니라 **존재하지 않는다.**

그래서 그 노가다를 이미 돌고 있는 자동배포 경로에 얹었다. 편집자의 추가 노동은 0이고,
사람이 하는 일은 **"이 상품 걸까요?" 에 예/아니오** 하나다.

## 1. 전체 흐름

```
[영상 분석]  회차 업로드 → content.analyze → beat/자막/요약
     │
     ▼
[채택]       사람이 추천 구간을 채택 → 클립 생성
     │
     ▼
[메타 생성]  clip.metadata → POST /api/clips/:id/generate-metadata
     │        Gemini 1콜로 제목·설명·태그를 만들면서 **상품 검색어를 같이** 뽑는다
     │        ⇒ 추가 API 콜 0 · 추가 원가 ₩0  (게이트 OFF면 프롬프트가 종전과 동일)
     │        저장: clip.commerce.queries = [{query, reason}]
     ▼
[링크 발급]  commerce.link 잡 (윈도우2 · commerce 레인)
     │        회사 계정 세션을 크롬에 주입 → 콘솔 내부 API 2콜
     │          POST /api/v1/search            검색어 → 상품 36개
     │          POST /api/v1/banner/iframe/url 상품 → 제휴 단축 URL
     │        저장: clip.commerce.links(전부 status=pending) + candidates(대체 후보 4개)
     ▼
[사람 검토]  웹 /commerce — 상품 사진·가격·장면 근거 + **실제 발행문 미리보기**
     │        승인 / 제외 / 다른 상품으로 교체
     │        ⇒ 승인한 것만 status=approved
     ▼
[발행]       distribution.publish → metaForChannel() 이 **발행 직전에** 조립
              설명란 끝에  ▼ 영상 속 상품 · 링크 · 대가성 문구
              ⇒ YouTube 설명란에만 (다른 채널은 안 붙는다)
```

### 핵심 설계 셋

| 결정 | 이유 |
|---|---|
| **발급 ≠ 게시** — 새 링크는 전부 `pending` | 파이프라인이 상품을 잘못 골라도(실측: 생화 꽃다발 장면에 드라이플라워) 방송사 채널로 바로 안 나간다. 자동화가 노동을 지고 판단은 사람이 한다 |
| **조립은 발행 직전** — 저장된 설명 본문에 굽지 않는다 | ① 대가성 문구를 사람이 지울 수 없어야 한다(누락 = 계정 정지) ② 링크가 늦어도 발행이 안 막힌다(링크 없으면 원문 그대로 나간다) |
| **상품 쿼리는 기존 호출에 편승** | 채널별 메타를 만드는 Gemini 콜이 이미 그 클립의 자막·요약·인물을 다 들고 있다. 따로 부르면 원가가 두 배가 된다 |

## 2. 사람 몫 / 자동 몫

| 단계 | 누가 | 빈도 |
|---|---|---|
| 상품 찾기 | 자동 (Gemini · 기존 콜 편승) | 클립마다 |
| 상품 → 쿠팡 검색 → 상품 선택 | 자동 (결정론 규칙) | 검색어마다 |
| 제휴 링크 발급 | 자동 (브라우저) | 검색어마다 |
| **어느 상품을 실제로 걸까** | **사람** | 클립마다 클릭 1~2회 |
| 대가성 문구 | 자동 (지울 수 없음) | 항상 |
| 설명란 삽입·발행 | 자동 (기존 배포 경로) | 발행마다 |
| 파트너스 로그인 | **사람** | 회사당 1회 (+세션 만료 시) |

### 상품 선택이 결정론인 이유

LLM 에게 순위·선별을 시키지 않는다 — 실행마다 결과가 바뀌면 측정할 수 없다. 규칙은 둘뿐:

1. 검색 응답은 이미 **쿠팡랭킹순**이다(플랫폼의 판단을 그대로 쓴다)
2. 성인용품·품절·여행상품 제외 → **후기 있는 상품 우선** → 없으면 1위

LLM 은 "이 장면에서 뭘 사고 싶어질까" 를 **서술**만 한다(추출이지 판단이 아니다).

## 3. 회사마다 계정이 다르다

**커미션 정산이 계정 단위다.** 한 계정에 subId 로 가르면 실적 보고서만 갈리고 **돈은 그 계정
하나로 들어와** 우리가 지급대행이 된다. 그래서 계정 자체를 회사별로 둔다.

```
commerce_account (tenant_id · RLS · migrations/0045)
  label               "ENA 법인"
  status              active | session_expired | disabled
  session_blob        AES-256-GCM 봉인된 로그인 세션 (COMMERCE_SESSION_KEY)
  session_updated_at / last_issued_at
```

잡은 `job.tenantId` 로 자기 회사 계정을 찾아 그 세션으로 발급한다 →
**커미션이 그 회사 법인 계정으로 직행**하고 우리는 돈을 만지지 않는다.

### 오귀속 가드 (이게 제일 중요하다)

계정을 잘못 고르면 A사 콘텐츠의 수익이 B사로 들어간다. 그런데 이 실패는 **에러가 아니라
"발급 성공"으로 보인다.** 그래서 방어가 셋이다:

1. **RLS** — 남의 회사 계정 행은 애초에 안 나온다
2. **테넌트 대조** — 잡 테넌트 ≠ 계정 테넌트면 중단 (`naver.publish` 와 같은 가드)
3. **폴백 없음** — 계정이 없으면 발급도 큐잉도 안 한다. 공용 계정으로 흘려보내지 않는다

### 세션이란 무엇인가

로그인 상태 = **쿠키 묶음**(쿠팡 기준 37개 · ~14KB JSON). 실측: 빈 브라우저에 그것만
주입하면 그 계정으로 로그인된다 — 2차인증까지 통과된 상태라 **아이디·비번보다 위험하다.**
그래서 `COMMERCE_SESSION_KEY` 로 봉인해 저장하고, **키가 없으면 저장 자체를 거부**한다
(평문 폴백 없음). 값은 로그·API 응답에 절대 싣지 않는다 — 바깥에는 있다/없다만 나간다.

## 4. 왜 윈도우2에서 도는가

`commerce` 레인은 **윈도우2 전용**이다(naver·download 와 같은 PC). 이유 둘 다 실측이다:

| 이유 | 실측 |
|---|---|
| **한국 IP** | 파트너스 콘솔은 Akamai 를 쓴다. 네이버·유튜브가 이미 해외 데이터센터 IP 를 막았다 |
| **화면 있는 크롬** | headless 는 **세션이 유효해도** 차단된다(Access Denied HTML). 봇 판정은 쿠키가 아니라 브라우저를 본다 |

⇒ Cloud Run 에 못 올린다. 데스크톱 세션이 살아 있는 PC 여야 한다.
회사가 여럿이어도 크롬을 N개 띄우지 않는다 — **잡마다 해당 회사 세션을 주입**하고 닫는다.

### DOM 이 아니라 API 를 쓴다

처음엔 화면을 몰았다(검색 → 카드 hover → '링크 생성' 좌표 클릭). 됐지만 셀렉터·오버레이·
좌표에 전부 의존해 콘솔이 조금만 바뀌면 깨진다. 트래픽을 떠 보니 콘솔이 하는 일은
**fetch 두 번**이 전부였다. 지금은 로그인된 페이지 컨텍스트에서 그 둘을 직접 부른다 —
유지보수 지점이 엔드포인트 2개로 줄었고, 쿠키·봇방어 값은 진짜 브라우저 것을 그대로 탄다.

> ⚠️ **비공식 내부 API 다.** 예고 없이 바뀔 수 있다 — 저볼륨(회차당 몇 건) 전제로만 쓴다.
> 최종승인(누적 판매 15만원) 후 **공식 딥링크 API** 로 갈아타면 이 레인은 없어지고 서버로 간다.

## 5. 안전 규칙 (전부 계정 정지와 직결)

| # | 규칙 | 코드가 지키는 방식 |
|---|---|---|
| 1 | **생성된 링크를 절대 열지 않는다** (자기 클릭 = 즉시 정지) | 우리 코드가 goto 하지 않음 + `link.coupang.com`·**`coupa.ng`** 로 나가는 요청을 라우트에서 전부 abort(이동뿐 아니라 하위 리소스까지) + 전 소스 스캔 테스트 + **화면에서도 `<a>` 가 아니라 복사 버튼** |
| 2 | **대가성 문구는 옵션이 아니다** | 링크가 있으면 항상 함께 나간다. 저장 본문이 아니라 발행 조립에서 붙어 사람이 지울 수 없다. 문구는 파트너스 콘솔 원문 그대로 |
| 3 | **제휴 링크 형식만 통과** | `link.coupang.com` https URL 만. 쿠팡 **상품** URL 도 거부 — 정산이 안 되는 맨 링크라 "링크는 걸렸는데 돈이 안 들어오는" 조용한 실패가 된다 |
| 4 | **확인된 채널만** | `COMMERCE_CHANNELS = ["youtube"]`. 네이버·인스타·틱톡은 링크가 클릭되지 않거나 정책 미확인이라 안 붙인다 |
| 5 | 상한 | 클립당 링크 3개 · 검색어 5개 · 후보 보관 4개 · API 호출 간격 1.2초 |

> ⚠️ **`coupa.ng` 를 빠뜨리면 샌다** (2026-08-27 실측). 콘솔에서 링크를 만들면 그 화면이
> 미리보기 배너 `<iframe src="https://coupa.ng/...">` 를 렌더하는데, 그 iframe 로드가 곧
> 제휴 리다이렉트라 **클릭으로 집계될 수 있다.** 초기 DOM 방식 실험 횟수만큼 리포트에
> 클릭이 찍혀 있었고, API 전용 경로로 바꾼 뒤로는 안 늘었다(현행 경로는 iframe 을 렌더하지
> 않는다). 그래도 라우트 차단에 두 호스트를 다 넣어 뒀다 — 우리 흐름은 둘 다 필요 없다.

대가성 문구(콘솔 원문):
> 이 포스팅은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

## 6. 설정

| env | 어디에 | 뜻 |
|---|---|---|
| `COMMERCE_LINKS_ENABLED` | 서버 · 워커 Job · **윈도우2** | 게이트. 기본 OFF · 오타·빈값도 OFF. ⚠️ **발행 조립에도 쓰인다** — 서버만 켜면 승인해도 안 붙는다 |
| `COMMERCE_SESSION_KEY` | 서버 · **윈도우2** | 세션 봉인 키(base64 32B). **양쪽이 같은 값**이어야 한다 — 다르면 복호화가 조용히 실패해 "세션 없음" 0건 발급이 된다 |
| `COUPANG_GAP_MS` | 윈도우2 | 내부 API 연속 호출 간격 (기본 1200) |
| `COUPANG_CDP_URL` · `COMMERCE_DEV_CDP` | 개발기만 | 미리 로그인해 둔 크롬에 붙는 개발 모드. ⚠️ 프로덕션 금지 — 수익이 그 계정으로 귀속된다 |

프로덕션 값의 정본은 `cloudbuild.yaml`(서버)과 Cloud Run Job env(워커)다. 수동 `services update`
로 넣은 값은 다음 배포에 지워진다.

## 7. 운영

### 회사 하나 붙이기 — 웹에서 시작한다

1. 그 회사가 **자기 법인 명의로** 쿠팡파트너스 가입
2. 웹 `/publish-channels` → 쿠팡파트너스 카드 → **"⬇ 쿠팡 로그인 도우미 다운로드"**
3. 받은 exe 를 더블클릭 → 브라우저가 뜨고 **두 번 로그인** —
   STEP D(어느 워크스페이스인지) · 파트너스(어느 계정인지)
4. 끝. 카드가 "연결됨" 으로 바뀌고, 그 워크스페이스의 링크는 이제 그 계정으로 발급된다

> **왜 exe 를 받아야 하나 — 웹만으로는 불가능하다.** 세션을 받으려면 쿠팡 도메인의 쿠키를
> 읽어야 하는데, `stepd.stepai.kr` 페이지는 교차 출처라 절대 못 읽는다(iframe 도 막힌다).
> 브라우저를 우리가 띄워야만 읽을 수 있어서, 네이버가 쓰는 것과 **같은 구조**의 작은
> 실행파일을 내려준다. pnpm·리포가 없는 PC 에서도 더블클릭으로 끝난다.
> 개발자는 `pnpm --filter @stepd/server commerce:login` 도 쓸 수 있다(카드의 '개발자용' 접기).
>
> 도우미 빌드·배포: `bun build --compile --target=bun-windows-x64 scripts/coupang-login-tool.mts
> --outfile stepd-coupang-login.exe` → `gs://stepd-media/tools/stepd-coupang-login.exe`
> (⚠️ 113MB · `.gitignore` 로 커밋 제외. `--smoke`·`--launch-test` 로 빌드 후 검증)

⚠️ 등록하는 계정이 곧 **커미션을 받는 계정**이다. 워크스페이스와 계정이 짝이 맞는지 확인할 것.

### 일상 운영

`/commerce` 화면 하나면 된다. 화면이 상태를 말한다:

| 화면이 말하는 것 | 뜻 | 할 일 |
|---|---|---|
| 계정이 등록되지 않았습니다 | 발급 보류(큐잉도 안 함) | 위 온보딩 |
| 로그인이 만료됐습니다 | 세션 죽음 | `commerce:login` 다시 |
| `COMMERCE_SESSION_KEY` 가 없습니다 | 서버 키 미설정 | Secret + 재배포 |
| 기능이 꺼져 있습니다 | 게이트 OFF | env |
| **발급 대기 N** | 상품은 찾았는데 링크가 없음 | "링크 발급" 클릭 |
| **대기 N** | 링크 있음, 사람 판단 필요 | 승인/제외/교체 |

### 안 될 때 보는 순서

1. 게이트가 **세 곳 다** 켜져 있나 (서버·워커 Job·윈도우2)
2. 윈도우2 워커 로그에 `claims=...,commerce.link` 가 있나
3. 그 PC 에 크롬이 있고 **로그아웃 상태가 아닌가** (headless 불가라 창을 띄워야 한다)
4. `COMMERCE_SESSION_KEY` 가 서버와 **같은 값**인가
5. 계정 status 가 `active` 인가 (`GET /api/commerce/account`)
6. 승인했는데 안 붙는다 → **worker-youtube Job** 의 게이트를 확인 (발행 조립이 거기서 돈다)

## 8. 원가·수익

- **상품 쿼리 추출: ₩0** — 기존 메타 생성 콜에 편승(추가 콜 없음). 프롬프트 +584자뿐.
- **링크 발급: ₩0** — 내부 API 호출, 브라우저 시간만.
- 메타 품질 영향 없음(A/B 실측): 제목·설명 동등, 응답시간 동일, **상품 없는 장면은 빈 배열**.
- 수익 쪽은 [commerce-revenue-model](../research/commerce-revenue-model-2026-08.md) 참고 —
  쿠팡 실효 커미션은 2% 미만이라 **쿠팡 단독으로는 크지 않다.** 진짜 레버는 네이버 쇼핑
  커넥트(3~50%)·유튜브 쇼핑 태그(5~15%)이고, 쿠팡은 **API 가 열려 있어 먼저 관통한 경로**다.

## 9. 제공자를 늘릴 때 — 레지스트리 (2026-08-31)

쿠팡이 코드 곳곳에 박히지 않게 접점을 `commerce.ts` 의 **`COMMERCE_PROVIDERS`** 한 곳으로 모았다.
URL 검증(`providerOfUrl`)·대가성 문구·설명란 조립이 전부 이 표를 따라간다.

**제공자 추가 = 항목 1개 + 발급기 1개 + 세션 등록.**

1. `COMMERCE_PROVIDERS` 에 `{ id, label, disclosure, linkPattern }` 추가
2. 발급기 모듈 (쿠팡은 `coupang-partners.ts`). 워커 `commerce.link` 가 provider 로 갈라 부른다
3. 회사별 계정 세션 등록 — `commerce_account.provider` 컬럼은 이미 있다

⚠️ **대가성 문구는 우리가 짓지 않는다.** 그 제공자 화면이 "이 문장을 기재하라" 고 명시한
원문을 그대로 옮긴다. 문구를 확인 못 한 제공자는 **레지스트리에 넣지 않는다** — 넣는 순간
그 문구로 발행된다. `commerce.test.ts` 가 ① 문구 없는 항목 ② 레지스트리 밖 하드코딩
(`link.coupang.com`·문구 문자열)을 막는다.

**링크의 제공자는 URL 이 정한다** — 저장된 `provider` 필드를 믿지 않는다. 옛 데이터엔 없거나
틀릴 수 있고, 그러면 엉뚱한 제공자의 문구가 붙는다(거짓 고지). 설명란에 나가는 문구도
**실제로 붙은 링크의 제공자 것만** 넣는다.

### 토스쇼핑 쉐어링크 — 조사 결과 (2026-08-31 · 미착수)

| 항목 | 확인된 것 |
|---|---|
| 제도 | 쿠팡파트너스에 대응. 상품 링크 공유 → 구매 시 수수료 |
| 수수료 | **10%** (쿠팡 평균 3~5%) — 붙일 이유가 이것이다 |
| 성립 | 클릭 후 **24시간 내 결제** · 정산 익월 25일 |
| API | **없다.** 공식 문서([sharelink-docs.toss.im](https://sharelink-docs.toss.im/))에 API 항목 자체가 없고 웹·앱 공유 버튼뿐. 문의는 sharelink@toss.im |
| 신청 | 크리에이터 참여 신청 폼 → **승인 3~5일**. 팔로워 요건은 없고 운영 중인 채널 정보 필요 |
| 구조 | 쿠팡과 같다 — 한국 IP + 화면 있는 크롬(윈도우2) · **회사마다 계정** |

**착수 순서**: ① (사람) 고객사별 쉐어링크 신청 — 승인이 임계경로 ② 발급기 구현
③ 레지스트리 항목 추가(문구는 그때 토스 화면 원문 확인) ④ 게이트.
쿠팡 경로는 **손대지 않는다** — 제공자마다 독립이라 토스를 붙이다 실패해도 쿠팡은 그대로 돈다.

**설계 확정 (사용자 2026-08-31): 폴백 없다 — 제공자마다 독립으로 붙인다.**
"토스 먼저 찾고 없으면 쿠팡" 같은 우선순위 로직을 두지 않는다. 각 제공자가 자기 링크를
발급하고, 설명란에는 **붙은 것들이 그대로** 나간다. 그래서 제공자가 늘어도 다른 제공자의
동작이 바뀌지 않는다(발급 실패도 서로 옮지 않는다).

여기서 따라오는 것 둘:
 · **대가성 문구도 각각 나간다.** 쿠팡 링크와 토스 링크가 같이 붙으면 문구도 둘 다 붙는다 —
   `withCommerceLinks` 가 붙은 링크의 제공자 집합에서 역산하므로 자동으로 그렇게 된다.
   쓴 제공자 문구가 빠지면 미고지라, 이건 줄이면 안 되는 자리다.
 · **`MAX_LINKS_PER_CLIP`(3)은 제공자 합산이다.** 둘을 같이 쓰면 상품 수가 그만큼 줄어든다 —
   실제로 붙여 보고 설명란이 길어지면 그때 제공자별 상한으로 나눌지 정한다(지금은 미정).

⚠️ 쿠팡과 같은 금기가 그대로 적용된다: **발급한 링크를 우리가 클릭하지 않는다**(자기 클릭 = 정지).
